# Аудит пути данных GarminDesk

Проверено 15 сентября 2026: `AppStore.swift`, `PythonBridge.swift`, `Connector/bridge.py` и локально установленный `garminconnect==0.3.15`. При проверке учётные данные, Keychain и реальные запросы Garmin не использовались. Четыре сценария ниже воспроизведены с `unittest.mock` и вымышленными значениями. Указанные в находках номера строк относятся к состоянию **до исправлений**.

После аудита по отдельному поручению исправлена сторона Swift: она принимает ранние события `session`, хранит безопасную структурированную диагностику, использует watchdog 210 секунд на каждом этапе и при ошибке записи Keychain отменяет запрос и прекращает использование сессии в памяти. `access_denied` и `security_challenge` больше не относятся к `auth`; в ветке настоящего `auth` ошибка удаления Keychain не подавляется. Проверка типов всех Swift-исходников приложения прошла. Изменения коннектора, отправляющего новые события, выполняются отдельно; эти результаты сами по себе не являются проверкой входа в Garmin.

## Находки

### P1 — успешная авторизация теряется при последующей ошибке загрузки

**Места:** `Connector/bridge.py:480–499`, `Connector/bridge.py:329–352`, `Sources/GarminDesk/AppStore.swift:170–179`.

`execute()` сначала завершает `client.login()` либо загружает прежнюю сессию, проверяет профиль, затем вызывает все группы данных. Только после `fetch_snapshot()` вызываются `client.dumps()` и возвращается сессия. Swift сохраняет её исключительно вместе с успешным `result`.

Поэтому достаточно успешного входа и ошибки 429 на второй группе данных: первая группа уже загружена, но наружу возвращается только `error.rate_limit`. Сессия не попадает в Keychain, пользователь остаётся неподключённым и после паузы вынужден снова вводить пароль. Полный сетевой отказ после успешного входа приводит к тому же результату.

При `sync` прежняя сессия сохраняется, однако обновлённые внутри процесса токены также не передаются. Библиотека действительно обновляет `di_token` и иногда `di_refresh_token` в `client.py:1378–1419`; обновление вызывается перед запросом при близком истечении токена и после 401 (`client.py:1641–1644`, `1682–1689`). Нельзя гарантировать дальнейшую пригодность старого refresh token после его замены; аудит не проверяет политику инвалидирования Garmin.

**Точное исправление:** отделить передачу сессии от результата данных. Добавить событие `session` с непрозрачной сессией и обработчик Swift, сохраняющий её в Keychain без требования `snapshot`. Передавать полученную после входа сессию до группы запросов; после успешного обновления DI-токенов немедленно передавать новую версию, когда содержимое изменилось. В закреплённой версии библиотеки это можно сделать обёрткой вокруг успешного `_refresh_di_token`, без записи токенов библиотекой на диск. Ошибка загрузки оставляет последнюю пригодную сессию и прежний снимок данных, сохраняя отображение самой ошибки. Событие сессии не должно заменять реальные измерения демоданными.

**Проверка исправления:** успешный вход → 429 на второй группе должен дать событие сессии и ошибку, без повторного вызова `login`; обновление токенов → последующий сетевой отказ должно сохранить новую сессию. Отдельно проверить ошибку Keychain, отмену и отсутствие записи сессии от уже отменённого `requestID`.

### P2 — таймер Swift завершает процесс раньше его собственного бюджета

**Места:** `Sources/GarminDesk/AppStore.swift:98–100`, `160–169`, `204–210`; `Connector/bridge.py:22–23`, `465–478`, `530–535`.

Swift даёт обычному запросу и продолжению после MFA 120 секунд. Python выделяет 180 секунд сетевой работы и отдельно 180 секунд ожидания MFA. В результате сетевой запрос, который ещё укладывается в собственный бюджет коннектора, принудительно завершается на 120-й секунде. Это особенно существенно для последовательного чтения 14 групп/профильных запросов: стандартный отдельный запрос библиотеки имеет timeout 15 секунд, а обновление DI-токена — 30 секунд.

Не требуется предполагать, что Garmin всегда отвечает медленно: любые восемь последовательных 15-секундных ожиданий уже исчерпывают более короткий таймер Swift. Коннектор не успевает вернуть своё итоговое состояние, а накопленные данные и новая сессия подпадают под предыдущую находку. Во время MFA обратное расхождение: интерфейс ждёт до 300 секунд, но процесс заканчивает ожидание после 180 и классифицирует дедлайн как `network`.

**Точное исправление:** согласовать бюджеты: например, процессу оставить 180 секунд на сеть и MFA, а внешнему watchdog дать 200 секунд для каждого этапа. При `mfa_required` перезапускать соответствующий внешний таймер, после кода — сетевой. Передавать истечение собственного дедлайна как `timeout`, который Swift уже умеет локализовать, вместо `network`. Для этого добавить ключ в `ERROR_MESSAGES` и разрешённый код протокола. Не увеличивать число повторных запросов.

**Проверка исправления:** с подменённым временем проверить переходы network → MFA → network и отсутствие внешнего завершения до внутреннего дедлайна. Для теста не нужны реальные ожидания по 180 секунд.

### P2 — неожиданный формат профиля ошибочно удаляет сессию

**Места:** `Connector/bridge.py:491–494`; `Sources/GarminDesk/AppStore.swift:189`.

После завершившегося входа профиль `{}` или ответ без `displayName` превращается в `BridgeError("auth")`. Swift трактует этот код как доказанную непригодность сессии и удаляет сохранённый токен. Отсутствие обязательного поля в ответе не является ответом сервера об ошибке авторизации. В библиотеке, например, HTTP 204 преобразуется в пустой объект (`client.py:1694–1711`), поэтому эти состояния принципиально различимы.

**Точное исправление:** классифицировать отсутствие/неверный тип `displayName` как `protocol`; добавить соответствующее безопасное сообщение коннектора. Удалять сессию только при подтверждённой ошибке авторизации. Не запускать новые группы данных без `display_name`, поскольку он нужен для их адресов.

**Проверка исправления:** успешный вход/восстановление сессии → пустой профиль должно вернуть `protocol`, сохранить доступную сессию и прежние измерения. Настоящий отказ авторизации должен по-прежнему переводить приложение в неподключённое состояние.

## Результаты воспроизведения без сети

Внутри `execute()` использовался `Mock` API; `login`, `loads`, профиль и все метрики заменены локальными ответами. Ни один настоящий клиент не создавался. В таблице число событий сессии учитывает только переданные через `emit` сообщения.

| Сценарий | Код | Вызовы login | Вызовы loads | Вызовы dumps | События сессии |
|---|---:|---:|---:|---:|---:|
| Вход успешен, вторая группа вернула 429 | rate_limit | 1 | 0 | 0 | 0 |
| Сессия восстановлена, вторая группа вернула 429 | rate_limit | 0 | 1 | 0 | 0 |
| Вход успешен, все группы завершились сетевой ошибкой | network | 1 | 0 | 0 | 0 |
| Вход успешен, профиль не содержит displayName | auth | 1 | 0 | 0 | 0 |

Сценарий ротации токенов подтверждён порядком вызовов и кодом установленного клиента, а не реальным обновлением токена Garmin.

## Периодичность и доступность показателей

- Каталог содержит **26 метрик**, но одна синхронизация выполняет **12 групп метрик + профиль + список устройств**, то есть 14 обычных запросов до учёта авторизации, обновления токенов и внутреннего повтора после 401. Это следует из `ENDPOINTS`, `fetch_snapshot()` и `execute()`.
- При стандартных 15 минутах это около **56 обычных запросов в час**; при разрешённых 5 минутах — **168 в час**, пока приложение работает. Настройка профиля не уменьшает число запросов: коннектор не получает список выбранных метрик. Ручные обновления добавляются к этому количеству.
- Эти числа **не доказывают причину текущего ограничения Garmin**. В исследованных исходниках нет подтверждённой безопасной квоты для аккаунта пользователя. Нельзя объявлять 56 запросов причиной 429 без данных сервера.
- Оптимизация с конкретным эффектом: кэшировать неизменившийся список устройств отдельно и не запрашивать его при каждом обновлении; проверять профиль и сохранять `displayName` в локальной сессии, а не читать его заново при каждом обычном sync. Повторять проверку при восстановлении/изменении сессии. Сохранить режим загрузки всех данных для обзора, но разрешить меньшую частоту редко меняющихся групп, например сна/HRV/веса.
- Все группы запрашиваются только за **сегодня по календарю Mac** (`bridge.py:324`). Например, вес без сегодняшнего взвешивания может отсутствовать, хотя вчерашний вес есть в Garmin Connect. Текущий код не обещает и не реализует поиск последнего значения за прошлые дни. Если продукт должен показывать «последний вес», необходим отдельный ограниченный поиск назад с датой измерения; нельзя подставлять вчерашнее значение как сегодняшнее.
- 26 поддержанных полей не означают все возможности часов fēnix 8. Успешный HTTP-ответ с отсутствующими полями не выдумывает измерения: они остаются отсутствующими. При пустом результате коннектор добавляет `no_data`; интерфейс сейчас отображает его общей подписью «Часть измерений недоступна». Для этого конкретного состояния точнее отдельный текст «Garmin не вернул измерения за выбранный день».

## Что уже работает согласованно

- Обычная нефатальная ошибка одной группы сохраняет успешно загруженные группы и добавляет `unavailable.GROUP`.
- Ошибки 429 останавливают дальнейшие запросы. После исправления Swift сохраняет между запусками паузу не менее 30 минут и учитывает `retryAfterSeconds` сервера, ограниченный семью днями. Это политика ожидания приложения, а не обещание времени снятия ограничения Garmin. Сетевой отказ не удаляет прежнюю сессию автоматически.
- При `auth` память переводится в неподключённое состояние, прежний снимок остаётся видимым с этим статусом. После перезапуска без сессии `init()` заменяет его демоданными (`AppStore.swift:66–68`): это различие состояний, которое стоит явно определить в продукте. Для устойчивого просмотра офлайн лучше сохранять последний реальный снимок с `isConnected=false` до явной команды удаления.
- Явное `disconnect()` теперь очищает память перед файловыми операциями, поэтому ошибка удаления кэша не позволяет таймеру восстановить сессию в текущем процессе. В ветке `auth` ошибка удаления Keychain пока подавляется через `try?`; если удаление не удалось, старый токен может быть прочитан при следующем запуске. Обработку ошибки нужно сделать явной, как в `disconnect()`.
- Чтение stdout происходит вне MainActor, stderr дренируется. Отмена закрывает stdin, завершает процесс и меняет `requestID`, поэтому запоздалое событие отменённой операции не применяется к AppStore. В этих местах блокирующей гонки при просмотре исходников не обнаружено.

## Граница вывода

Аудит выявляет воспроизводимые дефекты сохранения состояния и согласования таймеров. Он не устанавливает причину конкретного ответа Garmin при входе пользователя и не подтверждает доступность всех 26 метрик его аккаунта. Это можно проверить только после успешного подключения и чтения реальных данных; данный аудит таких действий не выполнял.
