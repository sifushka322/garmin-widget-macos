# Five widget types: simplification and migration audit

Reviewed on September 16, 2026. This records the local source audit and the agreed redesign contract. It is not evidence that a package has been released or that a normal macOS upgrade has passed.

## Product contract

The app provides five widget types. Summary has one editable, ordered selection of measurements. Day, Sport, Sleep, and Training calendar retain their fixed purposes. There are no user-created profiles, assignments, or content modes. One global widget appearance choice applies to all five types: colorful, light, or dark. Multiple instances of a type use the same settings.

| Type | WidgetKit kind | Purpose |
| --- | --- | --- |
| Summary | `GarminDeskSummary` — preserved | One coherent metric layout using the selected measurements in priority order; no embedded calendar. |
| Day | `GarminDesk.day` — new | Daily energy, movement, and health readings. |
| Sport | `GarminDesk.sport` — preserved | Readiness, recovery, and training measurements. |
| Sleep | `GarminDesk.sleep` — preserved | Sleep duration, score, stages, and related nightly readings. |
| Training calendar | `GarminDesk.training` — preserved | Completed activities and published scheduled workouts. |

Color and layout distinguish the purposes. Summary defaults to Body Battery, steps, sleep duration, stress, training readiness, resting heart rate, sleep score, intensity minutes, active calories, recovery time, and HRV. Users may choose other supported measurements, including weight and hydration. Its first available selected reading becomes the primary; unavailable readings are skipped, and unchecked readings never return as automatic fillers. If every selected reading is absent, the first choice remains visibly missing with no empty secondary cards. Selection order is preserved and at least one supported choice is required. Summary must not invent a combined health score. Calendar absence in the dedicated Training type remains distinct from a verified empty date; see [metric and calendar decisions](widget-product-decisions.md).

## Findings and settled decisions

**Widget identity is an upgrade contract.** Preserve the four existing kind strings, host and extension bundle identifiers, URL scheme, cache directory, and snapshot filename. Apple describes the kind string as the identifier used for a widget configuration; [StaticConfiguration](https://developer.apple.com/documentation/widgetkit/staticconfiguration) is appropriate when users do not configure individual widget instances. This does not guarantee that macOS immediately replaces a running extension or its gallery images.

**The old build selected a different product according to installed developer tools.** The static variant exposed four kinds, while the optional App Intents variant exposed one profile-configurable Summary. The redesign always builds five static configurations, independently of toolchain discovery. The optional App Intents prototype is retired explicitly. No public release used it; custom prototype installations may require removing and adding that widget again. Do not claim that preserving the kind also migrates its saved intent parameters.

**Static instances do not contain a saved profile UUID.** Their assignment was resolved from the host snapshot. Therefore old arbitrary UUIDs do not need to survive as new user-facing entities. The internal `WidgetProfile` type may remain as a render recipe and a compatibility wire type, but no profile data is saved in the new standalone preferences file.

**Old extension processes can briefly read a new snapshot.** A valid `version: 1` alone is insufficient: an old reader needs profiles and assignments to resolve Sport, Sleep, and Training. The new snapshot encoder writes a private four-recipe compatibility projection with stable UUIDs and matching assignments. The original reader also accepts only system, English, or Russian language values: the snapshot uses an English compatibility fallback for newer languages and a separate `widgetLanguage` field for the current reader's actual language. Standalone preference encoding omits every compatibility field and retains the actual language. This protects the transition without restoring a profile editor, and does not solve stale executable or gallery-image replacement by itself.

**New readers must also accept old files before the host first launches.** Decode old preferences and snapshots without requiring new fields. Preserve language, app appearance, refresh cadence, readings, timestamps, calendar coverage, connection state, and cache security rules. Unknown new widget-appearance values fall back safely. Legacy first-profile monochrome styling maps to light or dark using the old app appearance; other old styles map to colorful. Old names, assignments, selected metrics, and mixed layouts are intentionally replaced by the new type settings and must be described as such in upgrade notes. Preferences and snapshots without `summaryMetrics` receive the documented Summary defaults. A stored selection is sanitized by keeping each supported ID once in order; an empty or wholly invalid selection recovers to those defaults without resetting other preferences.

**Fetching cannot depend on removed profiles or on readings already available.** Request the union of dedicated fixed-purpose metric candidates and the selected Summary IDs, plus activity history and scheduled-workout coverage for Training. Deduplicate shared endpoint groups and preserve independent freshness, account ownership, backoff, and server-pause checks. Otherwise a first install could never discover readings omitted because its cache started empty. Appearance, language, and selection-order changes must not trigger extra requests. Adding an optional Summary group makes that group due; removing it stops future requests when no dedicated type needs it. Changes during an active batch coalesce and schedule missing groups after completion. Available-value filtering happens after normalization; a measured zero remains a value.

**Navigation must identify the widget purpose.** New links identify the fixed type. Continue accepting valid old `garmindesk://profile/<UUID>?slot=...` links: a recognized slot opens that purpose, otherwise open Summary. Do not require that the old UUID remain in preferences. App headers, status, and empty states must describe the content actually rendered.

**Gallery examples and live readings have separate contracts.** The gallery and explicitly marked app previews show filled synthetic measurements and sample completed/planned workouts, using the current week and month. The pure preview factory receives presentation settings, preserves language, appearance, and Summary choices, and never reads personal readings or publishes a timeline. Samples remain marked `isDemo`; rendering them also requires the entry's explicit preview flag. Ordinary widget timelines do not set that flag. First launch, disconnected live widgets, and cached legacy demo snapshots therefore remain honest empty/connection states. A preview flag is never persisted with account data, and the host clears either old or newly generated demo snapshots if they appear in its live cache.

**Removing profile controls is not sufficient.** Remove active profile creation, duplication, assignment, missing-profile states, content-mode choices, and old setup instructions from the app. Keep a direct Summary measurement chooser that cannot create profiles or alter dedicated types. All 12 language catalogs provide the new fixed-type instructions. Gallery instructions become: connect Garmin, choose a widget type and size, and place it. Unused legacy translation keys must not leak into the current product; the retired App Intents profile resources are removed from the bundle.

## Verification checklist

- Decode historical preferences with default, custom, empty, malformed, and dangling profile assignments; preserve independent settings while producing all five types and default Summary choices.
- Decode an old snapshot with the new reader before any host rewrite. Decode a newly encoded snapshot with a frozen legacy preference decoder and resolve each of the four old kinds. Verify that standalone preferences contain neither profiles nor assignments.
- Confirm exact existing kind strings, the one new Day kind, unique stable compatibility UUIDs, and purpose-based links including old-link fallbacks.
- Exercise a first connected sync with an empty cache: all required metric and calendar groups must be fetched once, including exactly the intended calendar months. Subsequent syncs must respect each group's cadence. Optional manually entered weight and hydration are not requested merely because the legacy editor once selected them; selecting them in the new Summary chooser does request their actual values.
- Verify Summary selection order, duplicate/unknown ID sanitization, empty-list recovery, old-preference defaults, persistence, and selected-only availability. Cached unchecked readings must not reappear. Editing Summary must leave the other four types unchanged.
- Retain tests for server pauses, expired sessions, cancellation, late responses, disconnect cleanup, account changes, partial calendar coverage, empty responses, and real zero readings.
- Render five types in three sizes and three appearances; inspect the single Summary metric layout, compact labels, dedicated calendar contrast, and empty/partial states. Check translated UI without relying on English fallback.
- Verify filled gallery previews separately: every supported measurement has a valid synthetic example, calendar dates and coverage follow the supplied date/timezone across month and year boundaries, and language/appearance changes preserve the same synthetic values. Test that live first-launch and legacy-demo cache handling still show no invented account readings.
- Build the same five static kinds with the supported toolchain. A custom request for the retired App Intents configuration must fail clearly rather than silently build a different widget bundle.
- Run the [normal upgrade scenario](widget-upgrade-validation.md) from the previous public release to the exact candidate. Keep its existing four desktop kinds in place, check the current icon and five-kind gallery, and add Day. No cache clearing, widget removal, extension termination, or NotificationCenter restart counts as a successful ordinary upgrade.

Source tests and image rendering establish model and presentation behavior. They do not replace the last checklist item, which remains a release gate on a Mac with a graphical session.
